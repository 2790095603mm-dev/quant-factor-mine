# Quant Research Agent 设计

日期：2026-09-28

## 目标与边界

在既有量化研究平台上增加一层**自主研究能力**：用户给一句自然语言请求（例如
「分析最近一年银行股低估值因子的表现」），Agent 自己选择数据工具、调用因子计算、
运行实验、检查异常、生成报告，全程带任务状态、失败重试、上下文管理与工具权限。

明确的边界：

- **不新增计算口径。** 因子计算、统一管线、单因子实验、回测、绩效口径全部复用
  既有 `qfm.factors` / `qfm.pipeline` / `qfm.simulation` / `qfm.portfolio`，
  Agent 层只负责编排，不重写任何一个算法。
- **不新增缓存机制。** 实验级缓存直接用 `qfm.jobs.JobService` 的内容寻址缓存，
  请求形状与既有页面同构，因此共享同一套缓存键语义。
- **不改动既有台账格式。** 实验落盘仍走 `qfm.research.ResearchStore` 的 JSON + CSV，
  Agent 的额外信息写在运行记录自己的目录里（`reports/agent_runs/<run_id>/`）。
- **默认不依赖 LLM。** 规划器默认是确定性的规则规划器；LLM 规划是可选增强。

## 为什么加在既有平台上是更合适的选择

「做一个 Agent Demo」最省事的做法是新建一个仓库：一个 `agent.py`、几个 mock 工具、
一段漂亮的 README。但那样做出来的东西无法回答面试里真正会被追问的问题：

| 追问 | 空壳 Demo | 本设计 |
| --- | --- | --- |
| 工具从哪来？ | `def get_price()` 返回随机数 | 12 个工具，底层是已跑通的因子库/实验引擎/回测 |
| 工具出错怎么办？ | `try/except: pass` | 异常分类 + 指数退避 + 结果校验，覆盖「无异常的静默降级」 |
| 上下文会爆吗？ | 玩具数据不会 | 摘要代替原文、超限外置 artifact、超预算折叠最旧，有压缩比统计 |
| Agent 会不会乱调工具？ | 没有约束 | 权限门：白/黑名单、只读模式、人工确认、次数与成本预算 |
| 结论可信吗？ | 编一个正的 IC | 异常检查 + 异常驱动的宽基对照 + 由证据推出的结论 |

所以这一层是**长在真实底座上的**，而不是旁边摆出来的。

## 总体架构

```text
                        ┌─────────────── 用户请求（自然语言）───────────────┐
                        ↓
                    Planner（规则规划 / LLM 规划，后者失败回落前者）
                        ↓  Plan：有序的 PlanStep
        ┌───────────────┴───────────────┐
        ↓                               ↓
   PermissionGate                   RetryPolicy
  （允许/拒绝/需确认/预算）      （分类 → 退避 → 重试 → 结果校验）
        └───────────────┬───────────────┘
                        ↓
                    ToolRegistry（12 个工具，契约声明 + 参数校验）
                        ↓
   ┌────────┬──────────┬──────────┬───────────┬──────────┬─────────┐
 resolve   load      describe  compute     run       check     generate
 universe  panel      panel    factor   experiment anomalies  report
   └────────┴──────────┴──────────┴───────────┴──────────┴─────────┘
                        ↓
           既有平台：qfm.data / qfm.factors / qfm.pipeline
                     qfm.simulation / qfm.portfolio / qfm.jobs
                        ↓
                  ToolContext（重对象工作集，不进上下文）
                        ↓
                   ContextManager（摘要 / 外置 / 折叠）
                        ↓
              AgentRun（轨迹 + 发现）→ 两类报告 + 运行记录落盘
                        ↑
                  异常驱动的重新规划（补跑宽基对照）
```

## 关键设计决策

### 1. 三层闸门，权限在重试之外

每次工具调用依次经过：

1. **权限门** `PermissionGate.check()` —— 不允许就记 `DENIED`，不执行；
2. **重试层** `call_with_retry()` —— 瞬时故障退避重试，确定性错误立即失败；
3. **结果校验** 工具自身的后置校验 —— 覆盖率不达标按瞬时故障处理。

权限必须在重试**之外**：否则一个被拒绝的调用会被重试三次，既浪费预算，又把
「这是权限问题而非故障」淹没在重试日志里。

第 3 道不做成运行时的通用钩子，而是让工具自己抛 `DegradedResultError`。理由是
**只有工具知道什么算结果不合格**：`load_panel` 关心覆盖率，`compute_factor` 关心
因子非空比例，`run_experiment` 关心有效交易日数。运行时猜不出这一层。

### 2. 重试必须能识别「静默降级」

既有 `DataLoader._fetch_one` 在单只股票拉取失败时只 `print` 一行然后返回 `None`，
最终仍返回一个看起来成功的面板。这是比抛异常更危险的情况：Agent 不知道自己拿的是
残缺数据。

因此重试层提供 `validate` 钩子，并定义 `DegradedResultError`（`TransientError`
子类）。`load_panel` 在覆盖率低于 85% 时抛它，于是「静默丢股票」被翻译成一个可
重试的错误。真实数据上实测触发过：某次请求 800 只、实际只加载到部分时，重试轨迹
里留下了完整的失败原因与退避时长。

### 3. 上下文：摘要进对话，重对象留工作集

真实数据下一次因子计算的返回值是 2000×800 的浮点矩阵（内存 10 MB 量级），
序列化进提示词会超出任何模型的窗口。所以：

- 工具返回 `(payload, summary)`：`summary` 手写、紧凑、只说「判断下一步所需的信息」；
- `payload` 留在 `ToolContext`（键如 `factor:bp`），供后续步骤复用，避免重复计算；
- 仍超限的内容写入 `artifacts/` JSON，上下文只留摘要 + 路径；
- 总长超预算时**从最旧开始折叠**成占位说明（不是删除，否则模型会以为该步骤
  未曾发生）；`pinned` 条目（请求、计划）永不折叠。

配套的硬约束：`_json_safe` 必须在鸭子类型分支**之前**拦截 pandas 对象。
`DataFrame` 和 `Series` 都有 `to_dict()`，一旦走到 `hasattr(value, "to_dict")`
分支，2000×800 矩阵会被逐值序列化——恰好把上下文管理的目的完全抵消。
（这条是本实现过程中实测发现的缺陷，现已修复并有回归用例。）

### 4. 异常驱动的重新规划，范围刻意做窄

`check_anomalies` 是主循环的转折点，它合并两类判据：

- 上游引擎已产出的告警（分层样本不足、信号覆盖率低、未产生成交）；
- Agent 层新增的判据（截面宽度、IC 显著性与方向冲突、IC 稳定性、换手侵蚀、
  单调性、超额为负、回撤）。

当出现 `high` 级别异常时补一段计划并继续执行。补救范围**只限换股票池**：

- 只对 `narrow_cross_section` / `layer_test_unavailable` 生效（`REMEDIATION_CODES`）；
- 最多补一轮（`max_replan_rounds`）；
- 不改变区间、因子定义与组合配置；
- 补齐的计划走同一套权限与重试闸门；
- 必须在计划 notes 里写明「为什么补这一步」。

之所以做窄：Agent 自主改研究设计是高风险行为。换股票池是唯一能通过「加对照样本」
消除疑虑而不引入新变量的操作。

### 5. 异常必须绑定到具体实验

一次请求可能对多个因子、多个股票池各跑一次实验。若异常只挂在「最近一次实验」上，
就会出现「用 A 实验的指标配 B 实验的异常」这种报告内部矛盾（实测出现过：主实验
年化超额 +2.25%，异常里却写「年化超额为负」）。

因此实验按 `因子名@股票池` 累积（`context.ledger["experiments"]`），异常按实验
分组返回 `by_experiment`，报告以**主实验**（本次运行第一个成功跑完的
`run_experiment`）为正文，对照实验单独成节。

### 6. 离线可自举：`data_cache/` 不在版本控制里

`data_cache/` 在 `.gitignore` 中，所以 clone 下来的仓库没有任何行情数据。如果
Demo 的第一步是「去 akshare 拉 800 只股票 6 年数据」，它大概率死在网络或限流上。

因此提供 `qfm/agent/synthetic.py`：确定性、零网络、零 IO 的合成面板。它不是
「随便造点随机数」，而是刻意为对齐真实场景设计：

- 行业标签用东财口径，`银行Ⅱ` 与真实缓存一致为 42 只 → 「截面不足 100 只导致
  分层检验不可用」这个问题在两种数据源下表现一致，异常检查逻辑不会只在合成数据
  上才生效；
- 字段齐全（`bvps / eps_ttm / roe / gross_margin / …`），价值/质量/成长族因子都
  有非空结果；
- 同时给 `factor` 与 `close_raw`，复权口径与真实数据相同（估值类因子用前复权价
  当分母是经典错误）；
- 行业标签**时点化**，行业变更在指定日期生效。

数据源由 `resolve_provider(mode)` 统一：`cache` 强制真实数据（缺失即失败，
不静默降级）、`synthetic` 强制合成、`auto`（默认）优先真实、回落到合成。
**每条链路都带 `source` 与 `note`，运行报告里以显著横幅标注合成数据**——
合成数据上的 IC 不是实证结论，这一点必须在报告里而不只是在文档里说清。

### 7. 默认规划器不是 LLM

Agent 架构里可复用的骨架是工具契约、权限门、重试、上下文管理、异常驱动的重新
规划；规划器是可插拔的一层。默认用规则规划器（`qfm/agent/vocab.py` 的词表 +
`planner.py` 的槽位解析）换来：

- clone 即跑，无需 API Key 与外网；
- 演示结果稳定可复现（同输入必然同计划）；
- 规划失败时行为可预测。

配置 `QFM_AGENT_LLM_BASE_URL` / `_API_KEY` / `_MODEL` 后切换到 `LLMPlanner`，
它用同一份工具目录规划，并校验：工具名必须出现在目录里、`arguments` 必须是对象、
`on_failure` 必须合法 —— 任何一条不满足就整份计划作废、回落到规则规划。
一个可能返回不可执行结果的规划器，会把校验负担推给上层；这里把校验收在规划器内部。

LLM 客户端用标准库 `urllib` 实现 OpenAI 兼容协议，不新增依赖。这个仓库的
`requirements.txt` 只有 7 个包，为一个**可选**增强引入 HTTP SDK 会让「clone 就能跑」
多一个失败点。

## 已知限制（未实现，不是已实现功能）

- **历史成分股缺失。** 按行业选池用的是某个时点的行业标签截面，对更早的区间会带
  幸存者偏差；这继承自既有平台的 `current-constituents-snapshot` 口径，报告里
  由 `build_data_snapshot` 的告警体现。
- **单进程同步执行。** 没有异步队列与并发；一个 runtime 实例可并发调用（运行态在
  `Session` 里而非 `self` 上），但没有 worker 池。
- **无取消与超时中断。** 只有重试层的 `deadline_s` 限制重试总时长，不支持中途取消。
- **权限门的「人工确认」没有交互式审批界面。** 接口已留（`approver` 回调），
  页面未接入；无审批人时 fail-closed 拒绝。
- **LLM 规划器未在 CI 中跑真实模型。** 测试用替身客户端覆盖了回落的各条路径。
- **合成面板的「价值效应」是人为植入的。** 这是为了让演示有真实内容可讲；
  报告里有显著横幅与文字说明，任何数字都不构成实证结论。
